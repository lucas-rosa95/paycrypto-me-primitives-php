# PIP00010 — Receiving-Only Account/Index Entry Point

Origin: [paycrypto-me/paycrypto-me-primitives-php#10](https://github.com/paycrypto-me/paycrypto-me-primitives-php/issues/10)

## Motivation

A multi-store consumer can assign a distinct Bitcoin account to each store and request a receiving address by account and address index. Its receiving request must not allow the caller to choose the internal/change branch. The existing generic public-address operation remains useful because other callers may need an explicit relative public path. The two request shapes serve different purposes and should compose without changing the generic operation.

## Materiality

The [approved PIP-0003 revision](https://github.com/paycrypto-me/paycrypto-me-primitives-php/blob/72c4fa1f0a2c9449a93071b55bf20f85b0008621/docs/pips/PIP-0003/PIP-0003.md) defines a public operation that accepts an extended public key and an explicit relative non-hardened path. Its scope excludes the reference application's fixed paths and account-depth assumptions from Primitives rules. Adding a separate Primitives-owned entry point that fixes the receiving branch and selects an account-level public key introduces a new contract at that boundary. [Issue #10](https://github.com/paycrypto-me/paycrypto-me-primitives-php/issues/10) therefore crosses the [Materiality Gate](../../specifications/paycrypto-pip-specification-v1.0.md#2-the-materiality-gate). This proposal adds that entry point; it does not amend or replace the approved PIP-0003 operation.

## Proposed change

Add a receiving-only Primitives entry point with separate integer `account` and `index` inputs, an explicit validated network, and an explicit address policy. `account` and `index` are each in the non-hardened index range `0..2³¹−1`; malformed or out-of-range values fail. Strings such as `0/1000` are illustrative notation, not a request grammar. The caller cannot supply a branch.

For the exact network, policy, and account requested, the entry point selects one account-level extended public key from an explicitly provisioned, immutable, public-key-only source. Missing, duplicate, malformed, or incompatible mappings fail without choosing another account or key. The provisioning party is responsible for binding each account number to its actual wallet key; serialized extended-key metadata cannot prove wallet ancestry. Primitives does not derive hardened accounts or accept private material.

The entry point invokes the existing generic public-address operation with the selected key and relative path `[0, index]`, using `0` as the fixed external receiving branch. It derives exactly the requested index: an invalid child fails without advancing. The result identifies the address, network, policy, and logical account/branch/index coordinates. For example, `account = 0, index = 1000` corresponds to `[0, 0, 1000]`, while `account = 1, index = 5` corresponds to `[1, 0, 5]`. These triples are logical wallet coordinates; the relative public paths from the respective account keys are `[0, 1000]` and `[0, 5]`.

The generic operation retains its extended-public-key plus explicit `relativePath` contract. Its callers continue to choose a bounded non-hardened relative path. Only the additional receiving entry point guarantees the fixed branch and rejects a caller-supplied branch. The concrete PHP types, source provisioning mechanism, and failure representation are chosen during qualification within these boundaries.

## Scope

This addition reuses the initial Bitcoin mainnet/testnet network definitions, strict extended-key version/policy compatibility, P2PKH, P2SH-P2WPKH, and P2WPKH address compositions, exact-path derivation, and delegated cryptographic and codec facilities governed by PIP-0003 and the Primitives Canonical. The additional entry point must preserve the same public-only, deterministic failure and provider-containment guarantees. Qualification must compare its result with a direct generic-operation call using the same account key and `[0, index]`, including failure cases.

Store-to-account assignment belongs to the consumer. Address allocation, index persistence, usage discovery, wallet ancestry authentication, seeds, private or hardened derivation, signing, spending, change-address requests through this entry point, and new networks or address policies are outside this proposal. No Execution Plan or production implementation is authorized before this proposal receives its own recorded approval.
