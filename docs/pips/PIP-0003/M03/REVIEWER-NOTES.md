## Scope of the claim

M03 provides **bounded research evidence ready for review**, not a production ECC selection or a usable public-address capability. The branch adds research probes, fixture/output records, a focused Composer lock and plan documentation. It does not add a runtime dependency to the library's production manifest or a public PHP API. PR #12 remains a draft pending review and the maintainer's manual merge decision.

The focused PHP candidates are Paragonie ECC 2.6.0 and Simplito elliptic-php 1.0.12. A source-pinned `1ma/secp256k1-php` 0.1.2 binding over libsecp256k1 0.8.0 supplies a separately implemented ECC comparison. All were exercised on PHP 8.3.35 and 8.4.26. The two PHP packages have distinct point implementations but share GMP; all three paths share the research CKDpub consumer and PHP HMAC/metadata code. Three adapters agreeing is therefore **not** three independent end-to-end BIP32 implementations.

## Observations and review risks

1. The initial PHP research adapters classified **every** parser exception as malformed input. The current adapters admit compressed point shape first and classify only source-pinned off-curve signals as `malformed_point`; unrelated exceptions and malformed parser outputs become `provider_failure`. Simplito's off-curve signal is a generic exception with an exact message, so an upgrade requires requalification. A fault that emits that identical signal remains indistinguishable at this boundary. See [parser-fault analysis](README.md#php-parser-faults-bounded-q12-distinction).
2. Native tweak-add returns `false` for more than one cause, including infinity and invalid scalar/opaque-key paths. The research classifier checks scalar/point admission, unchanged state and a separate same-library infinity confirmation. Injected comparator/confirmation faults were contained individually, but coordinated false results can still be misclassified, and a plausible wrong `true` result can appear successful. These are **synthetic counterexamples**, not observed defects in the pinned binding. The confirmation uses `ec_pubkey_create` with publicly derived HMAC tweak material through an API named for secret-key input; M05 must decide whether this route is acceptable inside a public-only adapter or keep the binding as reference-only. See [native analysis](README.md#native-false-source-path-and-bounded-resolution).
3. A deliberate HMAC key/message swap and a separate one-bit chain-code corruption made both PHP ECC adapters agree on wrong nodes. Full published-node comparison detected both; point-only comparison would miss the chain-code fault. The native adapter shares this consumer, so it cannot independently validate that part. See [common-mode analysis](README.md#shared-code-negative-control-and-ecc-lineage).
4. Local research images and source commits are identified in [reproduction](README.md#reproduction). The Debian package inputs used for the images/native build were not snapshot-pinned, so the work provides source-pinned results rather than bit-for-bit reproducible binaries. The focused Composer lock is research-only. GitHub CI runs the repository's `composer ci` and release checks on PHP 8.3/8.4; it does **not** rebuild the native extension or execute the complete standalone M03 probe matrix. A reviewer seeking independent confirmation should run the commands in the research record and compare the saved JSON outputs.

The most useful independent challenges are whether the published xpubs really
anchor the complete child nodes, whether each provider's malformed-point and
infinity signals support the claimed categories, and whether the native
confirmation route is suitable for a future public-only production adapter.
Please identify any additional boundary case that would change the M03 handoff
assessment rather than treating a green repository CI run as probe coverage.
