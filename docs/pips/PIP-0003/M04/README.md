# M04 codec, admission and definition research — bounded execution

This is the current M04 evidence handoff for [Issue #3](https://github.com/paycrypto-me/paycrypto-me-primitives-php/issues/3), under the [approved PIP-0003 proposal](https://github.com/paycrypto-me/paycrypto-me-primitives-php/blob/72c4fa1f0a2c9449a93071b55bf20f85b0008621/docs/pips/PIP-0003/PIP-0003.md) and the [execution roadmap](../EXECUTION-PLAN.md#execution-roadmap). It records bounded codec, admission, address-composition and definition research on PHP 8.3 and 8.4. The [independent follow-up review](https://github.com/paycrypto-me/paycrypto-me-primitives-php/pull/21#issuecomment-6243150128) accepted the earlier handoff at `6e8a512`; [PR #21](https://github.com/paycrypto-me/paycrypto-me-primitives-php/pull/21) merged it at [`85dbc5d`](https://github.com/paycrypto-me/paycrypto-me-primitives-php/commit/85dbc5d2a01794ddeb085dd3026a36df0b1bb9cd). No production provider, public API, or assembled capability is selected or claimed.

## Executed evidence

The [research manifest](M04-CODEC-COMPOSER.json) and [lock](M04-CODEC-COMPOSER.lock) pin four direct packages, with no transitive package dependencies: `tuupola/base58` 2.2.0 (`a2fac671`, MIT), `muvon/base58-codec` 0.1 (`753aeb34`, MIT), `bitwasp/bech32` 0.0.1 (`e1ea58c8`, Unlicense), and `cjpgdk/bech32` 0.1.2 (`179e48a8`, MIT). The lock SHA-256 is `8aeca13e02811d59ada980544b94bb167abd25d7df4b91b035b8fe9112fc279f`. Composer resolved and installed the exact graph under PHP 8.3.35; `check-platform-reqs` passed under PHP 8.3.35 and 8.4.26. `composer audit --locked --no-dev` reported no advisory or abandoned package for this lock at the checkpoint; this is not a security certification. Composer's strict manifest validation warns about intentionally exact research pins; it does not report a dependency error.

The [research consumer](codec-composition-probe.php) exercises the same address inputs across codec adapters and keeps output decoding out of the terminal Base58Check and SegWit generation adapters. Checked Base58Check decoding remains required for extended-key admission; decode-based output checks run in qualification. Its [PHP 8.3 result](codec-php83.json) and [PHP 8.4 result](codec-php84.json) agree after removing the runtime version field. The probe uses PHP's `hash()` for SHA-256 and RIPEMD-160, delegates Base58Check/Bech32 to the four libraries, and uses fixed protocol bytes for the witness-v0 redeem script. It does not implement a cryptographic primitive or standardized codec. It exercises:

The Tuupola checked API handles one version byte. Its semantic adapter first uses the same library's raw decoder to discover that byte, then invokes its checked decoder and compares the checked result to the raw payload without the checksum. This preserves all four extended-key version bytes while delegating checksum validation. Muvon's API accepts the complete payload as hex and returns an empty string for some invalid checked inputs. When either checked decoder fails, the adapter uses that candidate's raw decoder and checked encoder to distinguish an invalid checksum from an injected failure on self-consistent text. It rejects malformed successful decoder results. The terminal encoder checks only coarse return shape; qualification decodes its output with the other candidate. These checks use provider operations, not a local Base58Check implementation, and retain a same-library common-mode trust limit within input-decoder classification. Both adapters enforce exact 78-byte extended-public-key payloads outside the codec. These are research adapters, not production API choices.

The terminal Base58Check encoder no longer decodes its own output. Qualification uses the other candidate to compare returned payload bytes for all six public-version examples and the published BIP49/P2PKH addresses; published text supplies the external answer. The combined address composition calls the encoder but still decodes the input extended key during admission. Removing the terminal self-check therefore does **not** remove the decoder's Q12 obligations for malformed key input, nor the same-library failure-classification limit described above. Fault controls record the address encoder's runtime outcome separately from qualification; syntactically plausible wrong output remains a provider-trust limit for M05.

The pinned cjpgdk release emits three implicit-nullability deprecations when loaded under PHP 8.4. They are preserved in [the diagnostic record](codec-php84-diagnostics.txt). Semantic results still agree; the runtime diagnostic and the package's maintenance history require an M05 suitability decision. The two Bech32 packages both cite the wider BIP173/Pieter Wuille lineage, so adapter agreement is replacement evidence, not an independent proof of the checksum mathematics; the published BIP173/BIP84 vectors supply the external countercheck.

For SegWit address generation, the [adapter in this probe](codec-composition-probe.php) takes an admitted HRP and exact 20-byte witness program, calls the provider encoder, and checks only coarse return shape. A separate qualification helper decodes the result with the other candidate and compares the witness program; the published BIP84 text checks the actual output independently of either decoder. The helper is not called by the encoder or by the combined address composition. A self-decoding runtime check in the earlier M04 probe had made the decoder's Q12 ambiguity appear to block the generation operation. This was an execution/review boundary error, not a contradiction in the approved proposal or evidence of a BitWasp defect. The separate helper still has shared-lineage and decoder-classification limits; it is test evidence, not a public address-validation API or a guarantee against all incorrect provider output.

The [combined admission/composition probe](admission-composition-probe.php) uses the already pinned [M02 trial lock](../M02/M02-COMPOSER-TRIAL.lock), SHA-256 `afba6c348556431b1ae0ce218ab55af57ffd16b2185b5264ec300ecb82e5b0ff`, to add Paragonie ECC 2.6.0 and Simplito elliptic-php 1.0.12 to the four codec candidates. Its [PHP 8.3](admission-php83.json) and [PHP 8.4](admission-php84.json) result objects agree after removing the runtime version. One unchanged request-to-address research composition runs two checked Base58 adapters, two SegWit adapters and two ECC adapters: eight combinations for each of four published account keys. Every combination derives the exact `[0, 0]` public path from the [BIP49 testnet upub](https://github.com/bitcoin/bips/blob/3a10b5b5f0a7586df8928d580a3009744ebb2079/bip-0049.mediawiki#test-vectors), [BIP84 mainnet zpub](https://github.com/bitcoin/bips/blob/3a10b5b5f0a7586df8928d580a3009744ebb2079/bip-0084.mediawiki#test-vectors), and [SLIP-0132's mainnet xpub/ypub](https://github.com/satoshilabs/slips/blob/570ed55b7fde158f1116be34fc2faa35dada5912/slip-0132.md#bitcoin-test-vectors), then matches each published address. The BIP49/BIP84 results also match the published compressed keys; BIP49 matches its 20-byte key hash. The test-only Signet profile repeats the same upub/path/policy and address with a distinct result context. Both ECC adapters reject all three published BIP32 invalid public points after checked decoding, before HMAC.

Controlled point-admission exceptions or changed outputs, tweak exceptions or short outputs, HMAC exceptions or short outputs normalize to `provider_failure` in this research consumer. A confirmed infinity or order-sized HMAC left half becomes `invalid_child`; an invalid second-level child stops after exactly two HMAC attempts. Invalid point, unknown requested policy with a malformed key, and insufficient-depth inputs make zero HMAC calls; the unknown policy is rejected before key decoding. These controls narrow Q03/Q04/Q05/Q12 and complement the separate malformed-codec-output injections above; neither probe establishes safe diagnostics at a public API. The M03 independent ECC qualification and its native reference remain separate evidence; this combined probe uses the two PHP adapters only.

## Independent review follow-up

The [independent review of `7b1dee5`](https://github.com/paycrypto-me/paycrypto-me-primitives-php/pull/21#issuecomment-6240336419) requested two changes before M04 acceptance:

- **R1 — corrected:** The definition probe no longer uses order-sensitive PHP array identity for the version map. The saved [PHP 8.3](codec-php83.json) and [PHP 8.4](codec-php84.json) results now include a reordered-but-equivalent source that produces the same canonical immutable definition. Strict key/value matching and the negative wrong-mapping case still apply.
- **R2 — bounded, still open for selection:** An injected `BitWasp\Bech32\Exception\Bech32Exception` on the valid published BIP84 address now reports `provider_failure` on both runtimes because the fault hook establishes provider origin. Outside that controlled hook, the vendor's exception class can mean malformed input or provider malfunction. The research adapter still maps an uninstrumented native exception to `invalid_witness` to preserve the BIP173 invalid corpus; it cannot establish correct classification for a provider malfunction that throws the same type. The Q12 claim above is narrowed accordingly. M05 must resolve this ambiguity or reject this adapter before a public failure contract is exposed.

The [follow-up independent review of `6e8a512`](https://github.com/paycrypto-me/paycrypto-me-primitives-php/pull/21#issuecomment-6243150128) accepted R1 and the bounded R2 research disposition. It did not accept BitWasp for production; the uninstrumented native-exception ambiguity remains an M05 selection gate for any decoder boundary. The [later corrective re-review](#post-merge-corrective-re-review) separates this from the generation boundary.

## Post-merge corrective re-review

[Issue #25](https://github.com/paycrypto-me/paycrypto-me-primitives-php/issues/25) records a further review of the M04 research probe; [merged PR #26](https://github.com/paycrypto-me/paycrypto-me-primitives-php/pull/26) carries its corrective controls. On both PHP 8.3.35 and 8.4.26, an injected `DomainException('invalid_witness')` had crossed the decode override as an input failure, and an unknown requested policy paired with a malformed key had reached key decoding before request admission. The corrected probe maps the injected provider-boundary exception to `provider_failure` and rejects the unknown policy first. It also requires exact `invalid_witness` outcomes for the five published SegWit-valid addresses outside the initial P2WPKH policy, rather than accepting any non-success outcome.

A controlled scratch mutation of the pinned BitWasp decoder returning `false` for the valid BIP84 address exposed another misclassification: the uninstrumented research adapter had reported `invalid_witness`. The corrected adapter checks the native return shape before interpreting its fields, and reports `provider_failure` for that impossible output on both runtimes. Four fault controls now enter through the same raw-return branch. The mutation is evidence about adapter containment, not an observed BitWasp defect. An uninstrumented native `Bech32Exception` still has ambiguous provenance in the decoder. The earlier M04 review remains evidence for its exact reviewed revision; these later controls require their own review and do not select a provider or qualify a public API.

The corrective review found a **false negative in the earlier selection interpretation**: `segwitEncode()` called `segwitDecode()` on every successful output. That made a native decoder exception a failure of address generation and led the [earlier provisional triage](https://github.com/paycrypto-me/paycrypto-me-primitives-php/blob/85dbc5d2a01794ddeb085dd3026a36df0b1bb9cd/docs/pips/PIP-0003/M04/README.md#provisional-codec-candidate-disposition-for-m05) to block BitWasp as a SegWit candidate under Q12. The reviewed R2 statement remains correct **for a decoder boundary**; it does not establish that BitWasp's encoder is unsuitable for the approved generation capability. With a controlled scratch mutation that makes the pinned native decoder throw `Bech32Exception` for the valid BIP84 text, the revised encoder still succeeds on PHP 8.3.35 and 8.4.26, while the uninstrumented decoder reports `invalid_witness`; the mutation is not a BitWasp defect claim. The revised probe separates generation from decode-based qualification and records both boundary and qualification outcomes for every injected encode fault. In particular, a valid-looking wrong-program output is caught only by qualification; its runtime containment remains a provider-trust limit requiring M05 assessment. Neither BitWasp nor cjpgdk is selected or fully Q12-qualified by this correction.

The same responsibility crossing existed in `encodeChecked()`: it called `decodeChecked()` to verify every generated Base58Check string. The corrected terminal encoder no longer does so, and the research probe performs that comparison separately through the other candidate. This does not create the SegWit-style provider-selection false negative, because decoding a serialized extended key is independently required at request admission. It does expose an earlier overclaim that all injected encode faults were contained as runtime `provider_failure`: malformed text and a valid address for another payload pass the coarse encoder check and fail only qualification. The saved results now make that distinction explicit. Decoder failure classification and its same-library trust limit remain M05 work; these corrections require independent review at the new revision.

- Review the version/field and provider-fault precedence against the accepted M02 ordering. Unknown, private and multisignature version bytes use checked, synthetic public payloads; private key material is outside this public-only research. - Assess the cjpgdk PHP 8.4 deprecations and joint package security, maintenance, license and deployment tradeoffs before M05. M04's two real adapters per codec boundary have bounded agreement; no production selection follows from it.
