# M04 codec, admission and definition research — bounded execution

This is the executor's M04 evidence handoff for [Issue #3](https://github.com/paycrypto-me/paycrypto-me-primitives-php/issues/3), under the [approved PIP-0003 proposal](https://github.com/paycrypto-me/paycrypto-me-primitives-php/blob/72c4fa1f0a2c9449a93071b55bf20f85b0008621/docs/pips/PIP-0003/PIP-0003.md) and the [execution roadmap](../EXECUTION-PLAN.md#execution-roadmap). It qualifies bounded codec, admission, address-composition and definition slices on PHP 8.3 and 8.4. M04 remains open for review and merge; no production provider, public API, or assembled capability is selected or claimed.

## Executed evidence

The [research manifest](M04-CODEC-COMPOSER.json) and [lock](M04-CODEC-COMPOSER.lock) pin four direct packages, with no transitive package dependencies: `tuupola/base58` 2.2.0 (`a2fac671`, MIT), `muvon/base58-codec` 0.1 (`753aeb34`, MIT), `bitwasp/bech32` 0.0.1 (`e1ea58c8`, Unlicense), and `cjpgdk/bech32` 0.1.2 (`179e48a8`, MIT). The lock SHA-256 is `8aeca13e02811d59ada980544b94bb167abd25d7df4b91b035b8fe9112fc279f`. Composer resolved and installed the exact graph under PHP 8.3.35; `check-platform-reqs` passed under PHP 8.3.35 and 8.4.26. `composer audit --locked --no-dev` reported no advisory or abandoned package for this lock at the checkpoint; this is not a security certification. Composer's strict manifest validation warns about intentionally exact research pins; it does not report a dependency error.

The [unchanged research consumer](codec-composition-probe.php) changes only the codec adapter at each library-backed boundary. Its [PHP 8.3 result](codec-php83.json) and [PHP 8.4 result](codec-php84.json) agree after removing the runtime version field. The probe uses PHP's `hash()` for SHA-256 and RIPEMD-160, delegates Base58Check/Bech32 to the four libraries, and uses fixed protocol bytes for the witness-v0 redeem script. It does not implement a cryptographic primitive or standardized codec. It exercises:

The Tuupola checked API handles one version byte. Its semantic adapter first uses the same library's raw decoder to discover that byte, then invokes its checked decoder and compares the checked result to the raw payload without the checksum. This preserves all four extended-key version bytes while delegating checksum validation. Muvon's API accepts the complete payload as hex and returns an empty string for some invalid checked inputs. When either checked decoder fails, the adapter uses that candidate's raw decoder and checked encoder to distinguish an invalid checksum from an injected failure on self-consistent text. It rejects malformed successful results and checks encoded output by decoding it again. These checks use provider operations, not a local Base58Check implementation; they retain a same-library common-mode trust limit. Both adapters enforce exact 78-byte extended-public-key payloads outside the codec. These are research adapters, not production API choices.

The pinned cjpgdk release emits three implicit-nullability deprecations when loaded under PHP 8.4. They are preserved in [the diagnostic record](codec-php84-diagnostics.txt). Semantic results still agree; the runtime diagnostic and the package's maintenance history require an M05 suitability decision. The two Bech32 packages both cite the wider BIP173/Pieter Wuille lineage, so adapter agreement is replacement evidence, not an independent proof of the checksum mathematics; the published BIP173/BIP84 vectors supply the external countercheck.

The [combined admission/composition probe](admission-composition-probe.php) uses the already pinned [M02 trial lock](../M02/M02-COMPOSER-TRIAL.lock), SHA-256 `afba6c348556431b1ae0ce218ab55af57ffd16b2185b5264ec300ecb82e5b0ff`, to add Paragonie ECC 2.6.0 and Simplito elliptic-php 1.0.12 to the four codec candidates. Its [PHP 8.3](admission-php83.json) and [PHP 8.4](admission-php84.json) result objects agree after removing the runtime version. One unchanged request-to-address research composition runs two checked Base58 adapters, two SegWit adapters and two ECC adapters: eight combinations for each of four published account keys. Every combination derives the exact `[0, 0]` public path from the [BIP49 testnet upub](https://github.com/bitcoin/bips/blob/3a10b5b5f0a7586df8928d580a3009744ebb2079/bip-0049.mediawiki#test-vectors), [BIP84 mainnet zpub](https://github.com/bitcoin/bips/blob/3a10b5b5f0a7586df8928d580a3009744ebb2079/bip-0084.mediawiki#test-vectors), and [SLIP-0132's mainnet xpub/ypub](https://github.com/satoshilabs/slips/blob/570ed55b7fde158f1116be34fc2faa35dada5912/slip-0132.md#bitcoin-test-vectors), then matches each published address. The BIP49/BIP84 results also match the published compressed keys; BIP49 matches its 20-byte key hash. The test-only Signet profile repeats the same upub/path/policy and address with a distinct result context. Both ECC adapters reject all three published BIP32 invalid public points after checked decoding, before HMAC.

Controlled point-admission exceptions or changed outputs, tweak exceptions or short outputs, HMAC exceptions or short outputs normalize to `provider_failure` in this research consumer. A confirmed infinity or order-sized HMAC left half becomes `invalid_child`; an invalid second-level child stops after exactly two HMAC attempts. Invalid point and insufficient-depth inputs make zero HMAC calls. These controls narrow Q03/Q04/Q05/Q12 and complement the separate malformed-codec-output injections above; neither probe establishes safe diagnostics at a public API. The M03 independent ECC qualification and its native reference remain separate evidence; this combined probe uses the two PHP adapters only.

## Independent review follow-up

The [independent review of `7b1dee5`](https://github.com/paycrypto-me/paycrypto-me-primitives-php/pull/21#issuecomment-6240336419) requested two changes before M04 acceptance:

- **R1 — corrected:** The definition probe no longer uses order-sensitive PHP array identity for the version map. The saved [PHP 8.3](codec-php83.json) and [PHP 8.4](codec-php84.json) results now include a reordered-but-equivalent source that produces the same canonical immutable definition. Strict key/value matching and the negative wrong-mapping case still apply.
- **R2 — bounded, still open for selection:** An injected `BitWasp\Bech32\Exception\Bech32Exception` on the valid published BIP84 address now reports `provider_failure` on both runtimes because the fault hook establishes provider origin. Outside that controlled hook, the vendor's exception class can mean malformed input or provider malfunction. The research adapter still maps an uninstrumented native exception to `invalid_witness` to preserve the BIP173 invalid corpus; it cannot establish correct classification for a provider malfunction that throws the same type. The Q12 claim above is narrowed accordingly. M05 must resolve this ambiguity or reject this adapter before a public failure contract is exposed.

These changes await a follow-up independent review; a passing local probe is not the reviewer's acceptance.

## Review and handoff limits

- Review the version/field and provider-fault precedence against the accepted M02 ordering. Unknown, private and multisignature version bytes use checked, synthetic public payloads; private key material is outside this public-only research. The named mixed-invalid fixtures establish bounded ordering, not every possible pair of faults.
- Review the same-library round-trip trust limit of the codec adapters and the cjpgdk runtime diagnostics before treating either alternative as suitable. The current `category()` function is a research observer, not a public exception contract.
- Set concrete Primitives-owned public exception types and safe message/chain rules at M05, then verify them before M06 public exposure. The present scripts report research categories, not a public failure API.
- Assess the cjpgdk PHP 8.4 deprecations and joint package security, maintenance, license and deployment tradeoffs before M05. M04's two real adapters per codec boundary have bounded agreement; no production selection follows from it.
