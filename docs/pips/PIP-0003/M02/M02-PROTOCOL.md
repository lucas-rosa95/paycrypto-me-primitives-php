## O01 — Public derivation and invalid children

**M02 maintainer decision (2026-10-12): derive the exact requested path, with no implicit index advancement.** The maintainer rejected hidden allocation choices for consumer-supplied indices and accepted the exact-path behavior below. For a fixed admitted key, relative path, network definition, policy and functioning qualified dependencies, the operation has no allocation state or hidden index choices: it returns the corresponding address or the same semantic derivation failure. The earlier acceptance label was corrected in `beacf1c` before this decision was recorded. M03 must verify these semantics through real adapters and an independent reference before a production contract is frozen.

An exact-index CKDpub attempt is the semantic lower operation. It accepts one admitted parent and one non-hardened index, and reports either the child at **that index** or a distinguished invalid-child outcome. It never chooses another index. The receiving-address operation derives exactly the requested relative path, one attempt per level. An invalid child at any level ends the request with a distinguished invalid-child failure and no address. On success the result's derived path is exactly the requested path. It must not silently advance or return a partial address.

For each attempt, HMAC-SHA512 uses the parent's 32-byte chain code as key and the exact compressed parent key followed by the four-byte big-endian candidate index as data. Split its binary 64-byte result into 32-byte left and right halves. A left half interpreted as an unsigned scalar at or above the secp256k1 order is invalid. A zero left half is **valid under these rules**: the public point is unchanged, while the chain code, depth, parent fingerprint, and child number still reflect a new child. A finite nonzero tweak producing the point at infinity is invalid. Only a valid candidate's right half becomes the child chain code. HMAC/curve machinery remains delegated. [BIP32 CKDpub and serialization](https://github.com/bitcoin/bips/blob/3a10b5b5f0a7586df8928d580a3009744ebb2079/bip-0032.mediawiki) names the two invalid-child conditions and says to proceed with the next index. A consumer may submit another explicit request if it wishes; this operation does not choose that request. Zero-tweak validity is inferred from BIP32's invalid conditions and a valid finite parent.

The operation returns the exact derived relative path on success; every newly derived child's serialized number equals its corresponding requested component. The parent fingerprint is HASH160 of the immediate parent's compressed key, first four bytes. A previously imported hardened child number is historical metadata; it does not make a new hardened request legal. Primitives neither allocates indices nor retains consumer state. Fixtures must force invalid candidates at the first, intermediate, and last levels and show that each fails without advancement; also cover zero tweak, infinity, the last public index, and a parent at depth 255. These remain Q04–Q08 qualification cases, not passing tests.

The [M01 draft](../M01/M01-CONTRACTS.md) left O01 open and listed advancing-path Q05 cases. It remains historical assessed input. M03's Q05 execution must use the accepted M02 disposition: exact successful paths, failure at a forced invalid first/intermediate/last child, and no silent change to the requested path. O01 needs no further policy decision; provider behavior, independent results, and the public PHP representation of its failure remain qualification and O06/M05 work.

## O02 — Version, network, and policy compatibility

**M02 maintainer decision (2026-10-12): use the strict mapping for the initial capability.** The six admitted versions below each have one compatible network and policy. The caller must supply both network and policy explicitly; neither defaults from the key version or any other input. The version supplies an independent compatibility check that prevents accidental cross-policy address generation. This excludes older BIP49 xpub/tpub exports from the nested-SegWit path. The maintainer accepted that initial exclusion after reviewing the legacy-export tradeoff. M04 must qualify admission and rejection through real adapters before a production contract is frozen.

The proposed initial allowlist is the six Bitcoin public extended-key versions below. Admission compares all four decoded version bytes, never a textual Base58 prefix. A request supplies its network and address policy explicitly. Version meaning constrains compatibility but does not select the requested policy. This is a deliberately narrow admission policy based on the [SLIP-0132 registry at revision `570ed55`](https://github.com/satoshilabs/slips/blob/570ed55b7fde158f1116be34fc2faa35dada5912/slip-0132.md), [BIP32 serialization](https://github.com/bitcoin/bips/blob/3a10b5b5f0a7586df8928d580a3009744ebb2079/bip-0032.mediawiki), [BIP49](https://github.com/bitcoin/bips/blob/3a10b5b5f0a7586df8928d580a3009744ebb2079/bip-0049.mediawiki), and [BIP84](https://github.com/bitcoin/bips/blob/3a10b5b5f0a7586df8928d580a3009744ebb2079/bip-0084.mediawiki). BIP32 itself does not assign an address policy to an extended key.

| Network | Public version | Bytes | Admitted policy |
|---|---|---|---|
| Mainnet | xpub | `0488b21e` | P2PKH |
| Mainnet | ypub | `049d7cb2` | P2SH-P2WPKH |
| Mainnet | zpub | `04b24746` | P2WPKH |
| Testnet | tpub | `043587cf` | P2PKH |
| Testnet | upub | `044a5262` | P2SH-P2WPKH |
| Testnet | vpub | `045f1cf6` | P2WPKH |

The xpub/tpub choice is an application admission rule, not a claim that the BIP32 bytes cryptographically prevent other address forms. SLIP-0132 lists their address encoding as “P2PKH or P2SH” and describes earlier BIP49 exports that retained xpub bytes; the current [BIP49 extended-key rule](https://github.com/bitcoin/bips/blob/3a10b5b5f0a7586df8928d580a3009744ebb2079/bip-0049.mediawiki) specifies ypub/upub. The accepted initial mapping rejects an explicitly requested nested-SegWit address from xpub/tpub, even if the caller knows the key came from a BIP49 account. Accepting that legacy case later would require a deliberate compatibility revision, not a default policy inferred from xpub/tpub. Generic P2SH is outside this capability. No derivation path, account depth, or coin type is inferred from the registry's illustrative paths.

The registry also reuses some of these four-byte versions for other coins. The allowlist is meaningful only inside an explicitly supplied, validated Bitcoin network definition: matching version bytes cannot authenticate a key's chain provenance or prove that an upstream wallet used the requested policy. This is an input-context limitation, not a case the decoder can distinguish. Qualification must cover all six admitted version/network/policy combinations, plus checksum failure, an otherwise valid unknown version, private and multisignature versions, opposite-network intent, and a known version with a mismatched policy. A malformed serialized key fails as malformed input; a valid but unsupported version fails as unsupported; a recognized version with the wrong explicit network or policy fails as incompatible intent. None produces an address, inferred policy, inferred network, or fallback result. These failure meanings are required by the accepted O02 admission decision; O06/M05 still determine their public PHP representation.

For the initial validated definitions, mainnet uses P2PKH byte `00`, P2SH byte `05`, and SegWit HRP `bc`; testnet uses `6f`, `c4`, and `tb`. These values are corroborated by [Bitcoin Core chain parameters at `228877d`](https://github.com/bitcoin/bitcoin/blob/228877d7836a55c1d6fde90b0b7ba2d4c90248ab/src/kernel/chainparams.cpp) and [BIP173's HRP rules](https://github.com/bitcoin/bips/blob/3a10b5b5f0a7586df8928d580a3009744ebb2079/bip-0173.mediawiki). Bitcoin Core gives Testnet3, Testnet4, and Signet the same P2PKH/P2SH address bytes, `tb` HRP, and BIP32 test public-key version. This initial contract calls that shared address-parameter set “testnet”; it does not admit Signet as a public profile or claim chain identity from an extended key or address. P2SH-P2WPKH hashes the exact witness-v0 redeem script `0014` followed by the 20-byte public-key HASH160, as specified by [BIP141](https://github.com/bitcoin/bips/blob/3a10b5b5f0a7586df8928d580a3009744ebb2079/bip-0141.mediawiki). Constructing these owned protocol bytes uses fixed-width runtime byte operations; checksum and text encoding remain delegated.

**Future-profile counter-proof for O05/Q02:** M04 should use a test-only expanded profile registry with a separately identified Signet entry that reuses the testnet address parameters and public-version/policy mapping. It must demonstrate that the same key, path, and policy produce identical address text through the unchanged composition, while a result identifier reflects only the validated caller-selected context, not independently verified chain provenance. Equal version bytes, address prefixes, or HRPs must not be rejected as duplicate profiles or used to infer context. The initial public registry must reject an explicitly Signet-labeled definition until it is admitted; the test-only expanded registry must reject a Signet definition with wrong address parameters instead of falling back to testnet. This challenges schemas that hardcode a unique chain per address encoding and tests the Canonical's CP-02/CP-03 shared-behavior and data-variation properties without exposing Signet support in the initial public API. [BIP325](https://github.com/bitcoin/bips/blob/3a10b5b5f0a7586df8928d580a3009744ebb2079/bip-0325.mediawiki) defines Signet's challenge as a consensus parameter, not an address-encoding input; this Primitives address flow does not need to model that challenge.

O04's path rules and O05's definition/composition rules are accepted and await qualification; O06 remains a proposal. These rows do not prescribe public PHP class names.

**O04 maintainer decision (2026-10-12):** the admitted child-index limit is the non-hardened protocol range `0..2³¹−1`; do not narrow it based on an unqualified implementation assumption. M03/M04 must exercise its boundary values through the candidate adapters. The generic address operation rejects an empty path because the imported public node itself need not be a wallet-tracked payment address, as [BIP32 cautions](https://github.com/bitcoin/bips/blob/3a10b5b5f0a7586df8928d580a3009744ebb2079/bip-0032.mediawiki). The PIP00010 receiving entry point requires both `account` and `index` explicitly; zero is valid for either, and neither is defaulted.

**O03 consumer use case accepted by the maintainer (2026-10-12):** a multi-store consumer chooses its store-to-account mapping and supplies **separate `account` and `index` integer fields** to the receiving entry point. `0/1000` and `1/5` are discussion shorthand, not a string request grammar. Primitives fixes external branch `0` in that entry point; this does not restrict or replace the generic relative-path operation. The complete logical coordinates are `[0, 0, 1000]` and `[1, 0, 5]`, ordered as **account, fixed receiving branch, address index**. These triples express wallet locations, not relative public-derivation paths from one xpub or a three-component request field. The source provides the account-level xpub for each explicit network/policy/account tuple, so the actual generic-operation relative paths are `[0, 1000]` and `[0, 5]` from the respective keys. Missing, duplicate, malformed or incompatible entries fail; no other account or key is tried. Provisioning is explicit and public-key-only, with no allocation state in Primitives. A BIP44/49/84 account is hardened, so one account xpub cannot derive another account. Structural checks on an xpub's depth and child metadata cannot prove its real wallet ancestry; the party provisioning the source is responsible for the account-to-key binding. See [BIP32 public derivation and serialization](https://github.com/bitcoin/bips/blob/3a10b5b5f0a7586df8928d580a3009744ebb2079/bip-0032.mediawiki), [BIP44 path levels](https://github.com/bitcoin/bips/blob/3a10b5b5f0a7586df8928d580a3009744ebb2079/bip-0044.mediawiki), and [BIP84's reuse of that account structure](https://github.com/bitcoin/bips/blob/3a10b5b5f0a7586df8928d580a3009744ebb2079/bip-0084.mediawiki).

**O05 maintainer decision (2026-10-14):** accept validated, immutable, data-only network definitions and reuse the same derivation and address-policy compositions wherever only parameters vary. [Canonical §9](../../../canonicals/primitives/paycrypto-primitives-canonical-architecture-reference-v1.8.md#9-definitions-data-is-not-behavior) makes the distinction: a PHP array may be a definition source, but protocol code consumes validated semantics; the array itself is not the architecture. The previously investigated [BitWasp network factory](https://github.com/Bit-Wasp/bitcoin-php/blob/1.0/src/Network/NetworkFactory.php) constructs named network objects, while its [Litecoin network class](https://github.com/Bit-Wasp/bitcoin-php/blob/1.0/src/Network/Networks/Litecoin.php) holds parameter maps. These are comparison evidence, not an implementation pattern to reproduce. Primitives does not introduce a class or factory method per network merely to carry constants. An implementation may use a shared loader and a semantic value type; M05 chooses those PHP details. The validated identifier, not address bytes or HRP, supplies caller-selected context and keys the PIP00010 account source with policy and account. Two admitted profiles may share encoding parameters; that does not prove chain identity. Initial Signet intent remains unadmitted, while M04 tests a separately identified Signet profile in an expanded test-only registry.

The [approved PIP-0003](../PIP-0003.md) keeps the explicit relative-path operation and excludes fixed-path assumptions from that operation's boundary. The account/index entry point does **not** change its contract. [PIP00010's approved revision](https://github.com/paycrypto-me/paycrypto-me-primitives-php/blob/badb9cd4a5f4579174c8c7121558e9b38d566349/docs/pips/PIP00010/PIP00010.md) separately authorizes the fixed-branch and account-key selection boundary; [Issue #10](https://github.com/paycrypto-me/paycrypto-me-primitives-php/issues/10) carries the decision. The generic operation and O04 qualification can proceed under PIP-0003, while the extra entry point still requires implementation and qualification. The generic operation accepts relative paths as such; only the receiving entry point promises branch `0` and rejects any consumer-supplied branch.

For O06, a valid checked public key with a version outside O02 is an unsupported version; an admitted version for the other network is incompatible network intent; a supported address policy not admitted for that version is incompatible policy intent. An unknown requested policy is unsupported. Invalid Base58Check, wrong payload length, malformed point material and inconsistent root metadata are malformed input. Provider exceptions or impossible provider outputs are provider failures, never invalid children. An actual invalid child at a requested public index returns the invalid-child category, even at the last non-hardened index; a hardened or out-of-range requested index fails request admission. Q05 must show these outcomes are distinct and that no address or alternate index is returned. These categories are semantic meanings; M05 still chooses their PHP representation.

The accepted exact-path choice and strict initial version-policy allowlist must be verified against consuming use cases and qualified adapters before a public PHP API is frozen. Changing either within the approved public-address capability is an implementation decision; a material departure from the Canonical or approved PIP returns to the Materiality Gate.

Composer, pinned runtime images, CI, release guidance and M03–M08 verification now follow PHP 8.3/8.4; the earlier PHP 8.1 probes and trial lock remain historical evidence. No production provider dependency is selected by this decision.

### Second SegWit codec boundary probe

The [isolated cjpgdk probe](M02-CJPGDK-PROBE.php) ran on that PHP 8.1 image against cjpgdk source `179e48a8` and the [pinned BIP173 corpus](../M00/research/provider-refresh-2026-10-02/bip-0173.mediawiki). Its [raw result](M02-CJPGDK-PROBE.json) records 7/7 generic Bech32 valid, 12/12 generic Bech32 invalid (when the returned encoding enum is checked), and 3/3 valid SegWit-v0 examples. Its raw `decodeSegWit` accepted 2/10 BIP173 invalid SegWit examples: `tc1qw508d6qejxtdg4y5r3zarvary0c5xw7kg3g4ty` has an unadmitted HRP, and `BC1QR508D6QEJXTDG4Y5R3ZARVARYV98GJ9P` has a v0 program of invalid length. A separately constructed checksummed 21-byte v0 program was also accepted by the raw decoder, while its encoder rejected that length. These are wrapper obligations for the initial `bc`/`tb`, v0/20-byte capability, not evidence that the provider generated a wrong admitted address. The generic decoder may return an array with encoding enum `NONE` for an invalid checksum; checking only the returned array would misclassify that input.

To reproduce, mount cjpgdk's pinned source read-only at `/candidate`, this repository's `docs/pips/PIP-0003/M00/research/provider-refresh-2026-10-02` at `/evidence`, and the probe file at `/probe.php`; run `php /probe.php` in PHP 8.1. The probe aborts if the pinned BIP173 sections contain an unexpected number of vectors. No provider-independent result, semantic adapter, or production selection follows from this small corpus.

### Second checked Base58 candidate probe

The [isolated Muvon probe](M02-MUVON-PROBE.php) exercised [source `753aeb34`](https://github.com/Muvon/php-kiss-base58-codec/blob/753aeb34bbcb5d2bf902b8644efbca6052932b00/src/Base58Codec.php) on PHP 8.1.34 with BCMath. Its [raw result](M02-MUVON-PROBE.json) records 17/17 BIP32 public `xpub` checked round trips with the complete four-byte version retained, the [published P2PKH address example](https://github.com/OpenAssets/open-assets-protocol/blob/6c8502cf362d2902a3206dbc6cb75e791b55e0e8/address-format.mediawiki), and raw Base58 leading-zero preservation. For a corrupt checksum, invalid alphabet, and empty input, `checkDecode` returned an empty string rather than a typed error. The adapter must reject that result and enforce exact admitted payload lengths; a nonempty return alone is not admission. The provider accepts hex text rather than semantic bytes, so conversion and its validation must stay inside the adapter.

Its manifest has no production `require` block, but the [pinned source](https://github.com/Muvon/php-kiss-base58-codec/blob/753aeb34bbcb5d2bf902b8644efbca6052932b00/src/Base58Codec.php) calls `bc*` functions. Running the same probe on the prior PHP 8.1+GMP image without BCMath exited with an undefined `bcmul()` error. Any trial adapter must check that runtime facility explicitly and normalize its absence as an environment failure. The source was also installed through the trial Composer lock; repeating the probe against that installed copy produced the recorded JSON byte-for-byte.

For reproduction, mount the pinned `src/` directory read-only at `/candidate`, the stored [BIP32 snapshot](../M00/reviews/bitwasp-public-derivation/bip-0032.mediawiki) at `/evidence/bip-0032.mediawiki`, and `M02-MUVON-PROBE.php` at `/probe.php`; run `php /probe.php` with BCMath available. The probe aborts if the pinned BIP32 snapshot does not contain 17 public vectors. This is candidate feasibility evidence. It does not establish two qualified checked codecs, PHP 8.3 compatibility, safe behavior for the full malformed corpus, or provider replacement through an unchanged consuming composition.
