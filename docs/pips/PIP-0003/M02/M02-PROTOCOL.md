It proposes protocol dispositions for O01–O06 in the [M01 contract draft](../M01/M01-CONTRACTS.md) within the accepted [Primitives Canonical v1.8](../../../canonicals/primitives/paycrypto-primitives-canonical-architecture-reference-v1.8.md), and maps O07 candidates to later qualification. Maintainer review of the admission and operational choices remains open. No provider is selected and no implemented capability is claimed.

## O01 — Public derivation and invalid children

An exact-index CKDpub attempt is the semantic lower operation. It accepts one admitted parent and one non-hardened index, and reports either the child at **that index** or a distinguished invalid-child outcome. It never chooses another index. The receiving-address operation applies BIP32's instruction to proceed with the next index: at each path level, retry invalid candidates with the same parent and increment the index until a valid child is found. Then derive the next requested path component from that effective child. An invalid intermediate candidate therefore changes only that level's effective index; it must not return a partial path or retry the whole request from its original parent.

For each attempt, HMAC-SHA512 uses the parent's 32-byte chain code as key and the exact compressed parent key followed by the four-byte big-endian candidate index as data. Split its binary 64-byte result into 32-byte left and right halves. A left half interpreted as an unsigned scalar at or above the secp256k1 order is invalid. A zero left half is **valid**: the public point is unchanged, while the chain code, depth, parent fingerprint, and child number still reflect a new child. A finite nonzero tweak producing the point at infinity is invalid. Only a valid candidate's right half becomes the child chain code. HMAC/curve machinery remains delegated. This follows [BIP32 CKDpub and serialization](https://github.com/bitcoin/bips/blob/3a10b5b5f0a7586df8928d580a3009744ebb2079/bip-0032.mediawiki), which names the two invalid-child conditions and instructs proceeding to the next index; BIP32 does not prescribe a PHP API or operational retry budget.

The operation returns both requested and effective relative paths. Each effective component is the actual serialized child number at that level. The parent fingerprint is HASH160 of the immediate effective parent's compressed key, first four bytes. A previously imported hardened child number is historical metadata; it does not make a new hardened request legal. Fixtures must force invalid candidates at the first, intermediate, and last levels; a zero tweak; infinity; the last public index; and a parent at depth 255. These remain Q04–Q08 qualification cases, not passing tests.

## O02 — Version, network, and policy compatibility

The initial allowlist is the six Bitcoin public extended-key versions below. Admission compares all four decoded version bytes, never a textual Base58 prefix. A request supplies its network and address policy explicitly. Version meaning constrains compatibility but does not select the requested policy. This is a deliberately narrow admission policy based on the [SLIP-0132 registry at revision `570ed55`](https://github.com/satoshilabs/slips/blob/570ed55b7fde158f1116be34fc2faa35dada5912/slip-0132.md), [BIP32 serialization](https://github.com/bitcoin/bips/blob/3a10b5b5f0a7586df8928d580a3009744ebb2079/bip-0032.mediawiki), [BIP49](https://github.com/bitcoin/bips/blob/3a10b5b5f0a7586df8928d580a3009744ebb2079/bip-0049.mediawiki), and [BIP84](https://github.com/bitcoin/bips/blob/3a10b5b5f0a7586df8928d580a3009744ebb2079/bip-0084.mediawiki). BIP32 itself does not assign an address policy to an extended key.

| Network | Public version | Bytes | Admitted policy |
|---|---|---|---|
| Mainnet | xpub | `0488b21e` | P2PKH |
| Mainnet | ypub | `049d7cb2` | P2SH-P2WPKH |
| Mainnet | zpub | `04b24746` | P2WPKH |
| Testnet | tpub | `043587cf` | P2PKH |
| Testnet | upub | `044a5262` | P2SH-P2WPKH |
| Testnet | vpub | `045f1cf6` | P2WPKH |

The xpub/tpub choice is an application admission rule, not a claim that the BIP32 bytes cryptographically prevent other address forms. SLIP-0132 lists their address encoding as “P2PKH or P2SH”; this capability does not implement generic P2SH, and its explicit policy rejects a nested-SegWit request with those versions. No derivation path, account depth, or coin type is inferred from the registry's illustrative paths. Multisignature versions, private versions, unknown versions, and cross-network or cross-policy requests fail admission. A valid but unsupported version is distinguishable from an invalid checksum or malformed key.

For the initial validated definitions, mainnet uses P2PKH byte `00`, P2SH byte `05`, and SegWit HRP `bc`; testnet uses `6f`, `c4`, and `tb`. These values are corroborated by [Bitcoin Core chain parameters at `228877d`](https://github.com/bitcoin/bitcoin/blob/228877d7836a55c1d6fde90b0b7ba2d4c90248ab/src/kernel/chainparams.cpp) and [BIP173's HRP rules](https://github.com/bitcoin/bips/blob/3a10b5b5f0a7586df8928d580a3009744ebb2079/bip-0173.mediawiki). The current Bitcoin Core source gives testnet3 and testnet4 the same address bytes and HRP; this initial contract calls the address-parameter set “testnet” without claiming chain identity or compatibility with other network operations. P2SH-P2WPKH hashes the exact witness-v0 redeem script `0014` followed by the 20-byte public-key HASH160, as specified by [BIP141](https://github.com/bitcoin/bips/blob/3a10b5b5f0a7586df8928d580a3009744ebb2079/bip-0141.mediawiki). Constructing these owned protocol bytes uses fixed-width runtime byte operations; checksum and text encoding remain delegated.

## O03–O06 — Minimal operation boundary

These proposed choices are implementation contracts to test in M03–M07. They do not prescribe public PHP class names.

| ID | Decision | Qualification consequence |
|---|---|---|
| O03 | The public address request takes a serialized extended public key, a sequence of integer child indices, an explicit validated network definition, and one policy. A single admission boundary produces an internal immutable semantic extended-key value containing exact bytes and metadata. The result contains the address, network identifier, policy, requested path, and effective path. Direct lower-level composition consumes the same admitted value. | Q01/Q03/Q05 compare operation and direct composition; no provider object or private material crosses the boundary. |
| O04 | Accept an empty relative path: it addresses the imported public node. Path input is an array of integer values, with no string grammar or implicit absolute origin. Each index is 0 through 2³¹−1. Reject a path longer than remaining depth capacity (`255 − imported depth`) before derivation. Require a 64-bit PHP integer host for this initial representation. At each path level, allow at most 256 candidate attempts including the first; fail distinctly when this work budget is reached, and fail range exhaustion if the next candidate would enter hardened space. | Q04/Q05 check index and depth edges, empty paths, forced retries, budget and range exhaustion. The budget is an operational limit; it is not a BIP32 constant. |
| O05 | A validated definition supplies a network identifier, exactly one-byte P2PKH and P2SH versions, a lowercase SegWit HRP, and a map of admitted four-byte public versions to policies. The loader rejects missing, extra, duplicate, malformed, cross-network, or conflicting fields. It produces an immutable semantic view; definitions contain no providers, callbacks, scripts, or fallback rules. | Q02 checks two independently supplied valid definitions, rejection cases and reuse without mutation. Physical storage format remains an implementation choice. |
| O06 | Invalid public-child candidates are typed internal outcomes for the retry loop. Public failures distinguish malformed input, unsupported version/policy, incompatible network/policy, invalid definition, depth/range/budget exhaustion, and provider/environment failure. Validation order is definition and explicit request shape, checked key decode and structural admission, compatibility, then derivation and address encoding. No partial address is returned. Public diagnostics may name the failure category and path level but must not print extended keys, chain codes, or full wallet paths. Vendor exceptions are contained; there is no provider fallback. | Q12 must force every category, malformed provider outputs, missing runtime facilities, and vendor exceptions. Final exception/result PHP representation is set with the provider-backed contract in M05. |

The bounded 256-attempt choice and narrow version-policy allowlist should be challenged against consuming use cases before a public PHP API is frozen. Changing them within the approved public-address capability is an implementation decision; a material departure from the Canonical or approved PIP returns to the Materiality Gate.

The local image ID was `644b0f1c8f10e3751e5d3681588c806da7bcd6f98a6984bb64b96a2294ad31af`. Its output is [M02-PHP81-GMP-PROBE.json](M02-PHP81-GMP-PROBE.json), SHA-256 `4c18057bb0c2becc030bf36cf60336530942c2e91af13c4100fe8470dfb98195`.

### Second SegWit codec boundary probe

The [isolated cjpgdk probe](M02-CJPGDK-PROBE.php) ran on that PHP 8.1 image against cjpgdk source `179e48a8` and the [pinned BIP173 corpus](../M00/research/provider-refresh-2026-10-02/bip-0173.mediawiki). Its [raw result](M02-CJPGDK-PROBE.json) records 7/7 generic Bech32 valid, 12/12 generic Bech32 invalid (when the returned encoding enum is checked), and 3/3 valid SegWit-v0 examples. Its raw `decodeSegWit` accepted 2/10 BIP173 invalid SegWit examples: `tc1qw508d6qejxtdg4y5r3zarvary0c5xw7kg3g4ty` has an unadmitted HRP, and `BC1QR508D6QEJXTDG4Y5R3ZARVARYV98GJ9P` has a v0 program of invalid length. A separately constructed checksummed 21-byte v0 program was also accepted by the raw decoder, while its encoder rejected that length. These are wrapper obligations for the initial `bc`/`tb`, v0/20-byte capability, not evidence that the provider generated a wrong admitted address. The generic decoder may return an array with encoding enum `NONE` for an invalid checksum; checking only the returned array would misclassify that input.

To reproduce, mount cjpgdk's pinned source read-only at `/candidate`, this repository's `docs/pips/PIP-0003/M00/research/provider-refresh-2026-10-02` at `/evidence`, and the probe file at `/probe.php`; run `php /probe.php` in PHP 8.1. No provider-independent result, semantic adapter, or production selection follows from this small corpus.

### Second checked Base58 candidate probe

The [isolated Muvon probe](M02-MUVON-PROBE.php) exercised [source `753aeb34`](https://github.com/Muvon/php-kiss-base58-codec/blob/753aeb34bbcb5d2bf902b8644efbca6052932b00/src/Base58Codec.php) on PHP 8.1.34 with BCMath. Its [raw result](M02-MUVON-PROBE.json) records 17/17 BIP32 public `xpub` checked round trips with the complete four-byte version retained, the published P2PKH address example, and leading-zero preservation. For a corrupt checksum, invalid alphabet, and empty input, `checkDecode` returned an empty string rather than a typed error. The adapter must reject that result and enforce exact admitted payload lengths; a nonempty return alone is not admission. The provider accepts hex text rather than semantic bytes, so conversion and its validation must stay inside the adapter.

Its manifest has no production `require` block, but the [pinned source](https://github.com/Muvon/php-kiss-base58-codec/blob/753aeb34bbcb5d2bf902b8644efbca6052932b00/src/Base58Codec.php) calls `bc*` functions. Running the same probe on the prior PHP 8.1+GMP image without BCMath exited with an undefined `bcmul()` error. Any trial adapter must check that runtime facility explicitly and normalize its absence as an environment failure. The source was also installed through the trial Composer lock; repeating the probe against that installed copy produced the recorded JSON byte-for-byte.

For reproduction, mount the pinned `src/` directory read-only at `/candidate`, the stored [BIP32 snapshot](../M00/reviews/bitwasp-public-derivation/bip-0032.mediawiki) at `/evidence/bip-0032.mediawiki`, and `M02-MUVON-PROBE.php` at `/probe.php`; run `php /probe.php` with BCMath available. This is candidate feasibility evidence. It does not establish two qualified checked codecs, PHP 8.3 compatibility, safe behavior for the full malformed corpus, or provider replacement through an unchanged consuming composition.
