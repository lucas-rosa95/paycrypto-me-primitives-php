## Counterexamples and claim limits

- The BitWasp harness's six official non-hardened public edges and 17 public-key round trips match BIP32; its 30 address outputs are regression fixtures from the reference project, not independent address vectors. The research and earlier report make that distinction. The six cross-network fixture entries are deliberately excluded.
- The recorded `IL = 0`, `IL = n` and infinity injections distinguish raw BitWasp behavior from BIP32 CKDpub validity. The pinned BIP32 source defines invalid public children at `IL >= n` or an infinity point. A zero tweak alone is valid; the observed BitWasp rejection and infinity serialization therefore remain reference-provider findings. M02 subsequently chose exact requested-path failure semantics, and M03 qualified separate ECC/CKDpub research; those later results are not M00 evidence.
- The provider pack's 17 XPUB round trips show a provider-specific one-byte-version split, not full four-byte-version admission. The recorded empty checked decode returns an empty string, so its success-shaped result must not count as valid input. The four StephenHill cases compare raw Base58 only; the two PHP ECC APIs share GMP and do not establish independent mathematical verification. The research states these limits.
- [`probe.php`](../research/provider-refresh-2026-10-02/probe.php), lines 71–94, checks only that generic valid Bech32 inputs return arrays and records exceptions for invalid inputs. It does not compare decoded HRP/data to expected values or assert the vector counts at runtime. The saved results do show 7 valid and 12 invalid generic outcomes, plus 3 valid v0 and 10 invalid SegWit outcomes, matching the selected BIP173 sections. This supports the stated acceptance/rejection observation; it does not qualify a complete codec. M04 later adds stronger codec qualification.
- As a scratch negative control, replacing the first valid BIP173 Bech32 example `A12UEL5L` with `A12UEL5M` made `bech32_valid_generic[0]` record a checksum exception while the process still exited successfully. The other six valid outcomes stayed unchanged. Thus the JSON comparison exposes this injected mismatch, whereas the harness exit status alone does not. The original BIP173 snapshot and issued outputs were not changed.
- Both scripts are compact observational harnesses with a small `observe()` helper; [`inspect.php`](bitwasp-public-derivation/inspect.php) also isolates its source-manifest collection. Several dense one-line loops and inline classifications make future extension harder to audit, but no incorrect saved result was traced to them. Rewriting issued scripts would change historical evidence without a demonstrated correction. A future probe can separate vector extraction, invocation and expected-result checks, with explicit vector counts and decoded-value comparisons where those are qualification claims.

The repository's production `src/` contains only `.gitkeep` at the reviewed revision. The research scripts invoke PHP runtime operations and named provider codecs/ECC APIs, with a test-only HMAC fault seam in `inspect.php`; they contain no Primitives cryptographic algorithm or standardized codec implementation. Their compact script form does not create a production domain abstraction or a SOLID design concern requiring refactoring.

The original BitWasp checkout, installed vendor tree and historical container image identities remain unavailable. Reproduction uses the recovered lock, identical four-package source manifest and matching runtime versions, with the generated Composer-file differences above. This does not attest to the original environment byte for byte. PHP 8.1 ECC was skipped historically for lack of GMP; the newer PHP 8.3/8.4 research belongs to M03/M04.

## Finding, correction and review gate

**F01 — low severity; research-probe criterion and documentation overclaim, not an observed provider defect.** In `probe.php` lines 71–82, the valid generic Bech32 check accepts any array and the invalid checks only record outcomes. In [`public-address-provider-research.md`](../research/public-address-provider-research.md), the former line 57 said the selected BIP173 corpus "passed" and the D08/observation rows said generic vectors "behaved as expected." A full generic decode claim would require checking the decoded HRP/data and explicit vector counts; the probe recorded acceptance/rejection only. A provider returning an array with wrong decoded contents would satisfy that valid check. The scratch checksum mutation above demonstrates that a mismatch appears in JSON but does not cause probe failure. The affected claim is the strength of M00 feasibility evidence, not production behavior or the actual BitWasp output.

The jointly authorized focused correction keeps the issued script, JSON and manifests unchanged. The [research wording](../research/public-address-provider-research.md) now names the exact observed outcomes and the unchecked generic decoded contents. The [separate verifier](issue-28-bech32-evidence-check.py) asserts the pinned BIP173 vector inventory and saved outcome shape for both historical runtimes, including boolean return values and recorded exception fields. It passes the two issued JSON files and fails the scratch checksum-mutated output at `bech32_valid_generic[0]`. It does not claim to prove decoded generic payloads, runtime metadata or replace the later M04 qualification.
